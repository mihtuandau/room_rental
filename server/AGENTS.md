# RoomRent backend instructions

## Scope

These instructions apply to everything under `server/`.

The backend is a separate NestJS API. It owns authentication, authorization, business rules, persistence, moderation, queues, and the public API contract. It must not depend on frontend implementation details.

## Codex skills

Use the `roomrent-backend` skill under `.agents/skills/roomrent-backend` for every backend task. Read its project rules before editing, then load every applicable specialized skill:

- `add-nest-module`: controllers, services, DTOs, modules, and API endpoints
- `add-prisma-model`: models, fields, enums, relations, indexes, and migrations
- `auth-jwt-refresh-otp`: registration, login, logout, refresh, passwords, and OTP
- `bootstrap-project-setup`: application bootstrap, environment validation, Prisma module, and global filters
- `build-room-search-api`: filters, sorting, ranking, text search, and radius search
- `cloudinary-upload`: signed uploads and stored image metadata
- `saved-search-notification-job`: queues, cron jobs, and saved-search notifications
- `test-backend-feature`: focused unit, controller, guard, processor, integration, and e2e coverage
- `audit-backend-security`: evidence-based review of authentication, authorization, validation, data exposure, and abuse controls
- `build-admin-moderation-flow`: listing moderation, reports, user bans, audit trails, and approval side effects
- The relevant `prisma-*` skill for Prisma CLI or Prisma 7-specific behavior

Combine skills when a change crosses boundaries. Project security rules remain authoritative.

## Fixed stack

- NestJS with strict TypeScript
- Prisma 7 and PostgreSQL
- PostGIS and `unaccent` where required
- Passport and JWT authentication
- `class-validator` and `class-transformer`
- Swagger through `@nestjs/swagger`
- `@nestjs/throttler`
- BullMQ and Redis for background processing
- Cloudinary signed direct uploads
- Jest unit and e2e tests

Do not add libraries without a clear need.

## Commands

Run commands from `server/`.

```powershell
pnpm start:dev
pnpm lint
pnpm test
pnpm build
pnpm test:e2e
pnpm prisma validate
```

The lint script applies automatic fixes. Inspect resulting changes and do not overwrite unrelated edits.

For schema changes, use the current Prisma 7 configuration and create a new named migration. Never edit an applied migration.

## Security requirements

1. Keep authorization in NestJS guards and services. Do not rely on database RLS.
2. Validate every body, query, and route parameter with DTOs.
3. Keep global validation configured with whitelisting and rejection of unexpected fields.
4. Check resource ownership or administrator authorization before every protected mutation.
5. Store only password and OTP hashes. Never return or log hashes, raw passwords, OTP codes, tokens, or secrets.
6. Keep access tokens short-lived.
7. Keep refresh tokens revocable and protected by secure `httpOnly` cookies.
8. Restrict credentialed CORS to the configured frontend origin.
9. Rate-limit authentication, contact disclosure, search abuse, and other sensitive endpoints.
10. Convert internal failures to safe NestJS exceptions. Never expose raw SQL, database errors, or stack traces.
11. Never hard-code secrets. Read and validate configuration at application startup.
12. Log every landlord phone-number reveal in `ContactLog`.

## NestJS architecture

- Keep each domain in its own module with controller, service, DTOs, and module registration.
- Keep controllers thin: receive validated input, obtain the current user, call a service, and return the result.
- Keep business logic and authorization decisions in services.
- Pass user IDs and roles into services rather than passing raw request or response objects.
- Use `@CurrentUser()` and established guards and role decorators.
- Register every new module in `app.module.ts`.
- Use standard NestJS exceptions rather than inventing a parallel error system.
- Keep shared guards, decorators, filters, and DTOs under `src/common/`.

## API requirements

For every new or changed endpoint:

1. Add or update input DTO validation.
2. Apply authentication and role guards as appropriate.
3. Enforce ownership or administrative authorization in the service.
4. Add rate limiting where the operation is sensitive or abuse-prone.
5. Add descriptive `@ApiOperation` and response decorators.
6. Avoid returning internal or secret fields.
7. Add or update service tests.
8. Add e2e coverage for authentication, authorization, and key user flows.
9. Keep the response contract suitable for frontend type generation.

## Prisma and PostgreSQL

- Inspect `prisma/schema.prisma` before using any model, enum, relation, or field name.
- Reuse enums generated by Prisma Client when practical.
- Prefer Prisma Client queries.
- Use parameterized raw queries only for capabilities Prisma cannot express, such as PostGIS operations.
- Never concatenate user input into SQL.
- Never use `$queryRawUnsafe` with untrusted or interpolated input.
- Create a new migration for every schema change.
- Never hand-edit an already-applied migration.
- Commit schema and migration changes together when asked to commit.
- Use soft deletion for records that must remain auditable.
- Exclude deleted records from public queries.
- Preserve restrictive deletion behavior for relations that must survive user removal.

## Data conventions

- Store money as integer VND, never floating point.
- Keep `city`, `district`, and `ward` in separate fields.
- Use `unaccent` for appropriate Vietnamese text search.
- Keep `RoomType` values aligned with the Prisma enum.
- Store latitude and longitude with the established geographic representation.
- Keep PostGIS geography values synchronized through the established migration or database mechanism.

## Listings and moderation

- Newly created rooms default to `pending`.
- Only administrators may approve, reject, hide, restore, or otherwise moderate listings.
- Record every administrative status change in the moderation audit trail.
- Public list and detail endpoints return only `active`, non-deleted listings.
- Rank verified listings before unverified listings.
- Preserve anti-fraud and verification behavior.
- Do not allow owners to bypass moderation through ordinary update endpoints.

## Authentication

- Hash passwords with the configured strong password hashing implementation.
- Never select or serialize password hashes unless an internal authentication operation requires them.
- Sign access and refresh tokens with different secrets.
- Keep refresh-token revocation tied to the established token-version or stored-session mechanism.
- Revoke old refresh sessions after logout, password changes, or other security-sensitive events.
- Protect cookie settings appropriately for the deployment environment.
- Hash OTP codes, enforce expiry and attempt limits, and never log production OTP values.

## Search

- Always filter public search to active, non-deleted rooms.
- Keep verified-first ranking as the first ranking condition.
- Use Prisma filters for ordinary price, area, type, amenity, and status filters.
- Use parameterized PostGIS queries for radius search.
- Validate pagination, sort fields, coordinates, radius, and numeric ranges.
- Preserve deterministic secondary ordering for stable pagination.

## Uploads

- NestJS issues short-lived signed Cloudinary upload parameters.
- Clients upload bytes directly to Cloudinary.
- The backend validates and stores confirmed `public_id` and secure URL values.
- Verify ownership and intended resource type before issuing signatures or confirming uploads.
- Do not retain uploaded image bytes on the API server.

## Background jobs

- Enqueue notification work outside request transactions.
- Keep processors idempotent because jobs may retry.
- Prevent duplicate notifications for the same saved search and room.
- Rate-limit outbound notifications per user.
- Use event-driven enqueueing with periodic scanning only as a recovery mechanism.
- Log failures with enough internal context for diagnosis without exposing secrets.

## Verification

Choose checks based on the change:

- DTO, controller, or service logic: targeted Jest tests and build
- Authentication or authorization: targeted tests plus relevant e2e tests
- Prisma schema: `pnpm prisma validate`, migration checks, generated client checks, and build
- Module wiring or configuration: build and relevant startup/e2e checks
- Queue processing: processor/service tests and idempotency cases
- Broad changes: lint, test, build, and e2e as warranted

Report any check that cannot run and why.
